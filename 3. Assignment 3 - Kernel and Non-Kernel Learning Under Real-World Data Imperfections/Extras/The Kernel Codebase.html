00 — What this is

Every file here does one thing to one table.

That table is K, the kernel matrix. It holds the similarity between every pair of your data points. Build it, and the four algorithms become short.

The table itself

Six points sit on a line. Cell (i,j) is how similar point i is to point j under the RBF kernel. Drag γ and watch the whole method change character. This single control is the difference between "every point is a neighbour" and "every point is an island."

What you should be able to do at the end

Point at any line in these five files and say three things: what it computes, which formula it is, and why it is written that way and not the obvious way. The third one is where marks are won, because most of the odd-looking lines in this codebase exist to dodge a specific numerical or memory problem.

A constraint, stated up front

This page is one offline HTML file with no libraries, so a maths renderer like KaTeX or MathJax — which would have to load from a CDN — is not available. Every formula here is therefore set by hand in HTML and CSS using real Unicode symbols. It looks slightly plainer than LaTeX output, and that is the only visible cost of the offline requirement.

One thing I could not check

kpca.py imports LogisticRegression from .logistic_regression, and every file imports from utils/kernels.py. Only kernels.py was given to me. So everything said about kernels.py is read from its source; everything said about LogisticRegression is limited to what the calling code in kpca.py proves about it (that it accepts lr, n_iters, reg_lambda, and exposes fit, predict, predict_proba, classes_). I have not invented anything about its internals.

01 — The idea underneath

Three ideas. Everything else is mechanics.

Read this section once and the code stops being mysterious. Skip it and you will be memorising line noise.

Idea 1 — A dot product is a similarity score

Take two data points, x and z. Their dot product x·z is big when they point the same way and small when they don't. That is all a dot product is: a number saying "how alike are these two."

Now here is the observation the whole field is built on. Write out linear regression, PCA, SVM, nearest neighbours — and in every one of them, the data only ever shows up inside a dot product. Never alone. Only ever paired up and multiplied.

Show me that's true, for distance at leastworked example

Squared distance looks like it needs the raw points. It doesn't:

‖x − z‖2 = (x − z)·(x − z) = x·x + z·z − 2 x·z Three dot products. The raw coordinates never appear on their own.

Hold onto this line. It reappears literally, as code, in kernel_knn.py and again inside rbf_kernel.

Idea 2 — The kernel trick

Your data isn't separable by a straight line. The classic fix: invent extra features. Map each point through some function φ into a bigger space where it is separable, then run the linear method there.

The problem: that space might have a thousand dimensions. Or infinitely many. Computing φ(x) would be impossible.

The escape: you established in Idea 1 that you never need φ(x) by itself — you only ever need φ(x)·φ(z). So if some cheap function k(x,z) happens to return exactly that number, you can run the whole algorithm in the huge space without ever visiting it.

k(x, z) = φ(x) · φ(z) The kernel: a shortcut to a dot product in a space you never build

The trick, drawn

How to read it. Grey dashed = the honest, impossible route. Gold = what the code actually runs. The dashed box is drawn dashed on purpose: φ appears nowhere in the codebase. Search for it — it isn't there. That absence is the trick working.

Idea 3 — The Gram matrix, and why it's your bill

You don't call k on one pair. You call it on every pair, and store the answers in a square table K where Kij = k(xi, xj). That is the Gram matrix — the heatmap at the top of this page.

It has three properties worth stating out loud, because each one causes a specific line of code later:

  • It's symmetric. Kij = Kji, since similarity doesn't care about order.
  • It's usually positive semi-definite. That's what lets kernel_ridge.py ask for the fast Cholesky solver — and why it needs a fallback when the poly kernel rounds its way out of PSD.
  • It costs n2. 10,000 points → 100 million entries → 800 MB in float64. This is the wall every kernel method hits, and it's why kernel_matrix_bytes_ exists in four of these five classes: someone wanted that cost measured, not assumed.
The sentence that unlocks the codebase

Once K exists, none of these algorithms ever look at your data again. Kernel ridge solves a linear system in K. The SVM indexes into K. KPCA takes eigenvectors of K. Kernel KNN subtracts entries of K. The data is gone. Only the table remains. Say this in an exam and you have shown you understand kernel methods.

Why the answer is always "a weighted sum of training points"representer theorem

Look at the prediction line in three different files:

K_test @ self.alphakernel_ridge.py
K_test @ (self.alpha * self.y_train) + self.bkernel_svm.py
K_test_centered @ self.eigenvectorskpca.py

All three are the same shape: a row of kernel values against the training set, dotted with one learned coefficient per training point.

f(x) = Σi αi k(xi, x) the only form the answer is ever allowed to take

This isn't a coincidence or a convention — it's a theorem (the representer theorem). For this family of problems, the optimal solution provably lies in the span of the training points. So the entire learning problem collapses from "find a function" down to "find n numbers." Those n numbers are self.alpha. Every model in this codebase is a different way of computing them:

  • Ridge: solve a linear system → solve(A, y)
  • SVM: iterate a constrained optimiser → _run_smo()
  • KPCA: take eigenvectors → eigh(K_centered)
  • KNN: don't learn them at all; set them to 1/k for the neighbours and 0 for everyone else

That last line reframes KNN as a kernel method with hard-coded, data-dependent α. Worth having ready.

02 — How the files connect

One supplier, four customers.

kernels.py is the only file that knows what a kernel is. The other four just order matrices from it.

How to read it. Gold box = the supplier. The purple line is a one-way street: kernels.py imports nothing from the models and knows nothing about them. It hands back a NumPy array and stops caring. Each customer box names the one operation it performs on that array — that operation is the algorithm.

The four-line contract every model obeys

Once you see this shape you can read any of the four files in about ninety seconds, because they are all the same file with one line swapped.

def fit(self, X, y):
    self.X_train = X.copy()             # 1. keep the data — prediction needs it
    K = compute_kernel_matrix(X, ...)     # 2. build the n×n table
    self.alpha = <the one interesting line>  # 3. THE ALGORITHM

def predict(self, X):
    K_test = compute_kernel_matrix(X, self.X_train, ...)  # m×n, test vs train
    return K_test @ self.alpha                          # the representer form
The shape rule that prevents most bugs

compute_kernel_matrix(X) with one argument gives you n×n (train vs itself). compute_kernel_matrix(X_test, X_train) with two gives you m×n (test rows, train columns). Order matters: rows follow the first argument. Every predict in this codebase puts test first and train second, so K_test @ alpha is (m×n)·(n,) → (m,) — one prediction per test point. If you ever flip those arguments the shapes still might multiply, and you will get silent nonsense.

03 — utils/kernels.py

The supplier: three kernels and three utilities.

This is the file to know cold. If you can map each function here to its formula, the other four files are bookkeeping.

K utils/kernels.py
Role in the pipeline: builds K — and provides two shortcuts for reading it cheaply.

linear_kernel — the control condition

k(x, z) = x⊤z + c feature map: φ(x) = x. No transformation at all.
def linear_kernel(X, Y=None, c=0.0):
    if Y is None:
        Y = X
    return X @ Y.T + c

The feature map is the identity — this kernel goes nowhere. That makes it the baseline you report against: if RBF doesn't beat linear on your data, the data was linearly separable and the whole apparatus bought you nothing. It's also the honest reference point for the memory argument, because linear kernel methods have an O(d2) primal alternative while RBF does not.

polynomial_kernel — finite, explicit, and it can explode

k(x, z) = (α · x⊤z + c)d feature map: all monomials of the coordinates up to degree d. Finite, but large.
def polynomial_kernel(X, Y=None, degree=3, alpha=1.0, c=1.0):
    if Y is None:
        Y = X
    return (alpha * X @ Y.T + c) ** degree

Unlike RBF, this kernel's feature space is real and countable. Expanding (x·z + 1)2 for 2-D points gives you a feature map containing x12, x22, x1x2, x1, x2, 1. Products of coordinates — that's how it becomes nonlinear.

The one that causes trouble downstream

Look at the scale. If x·z is around 20 and d=3, then k ≈ 213 ≈ 9261. Raise the degree and the entries of K grow without bound. Two consequences you can point to as code:
• kernel_ridge.py has a try/except fallback whose comment says exactly this — huge dynamic range makes K lose positive-definiteness to rounding, and the Cholesky solver refuses.
• kpca.py guards with if self.eigenvalues[i] > 1e-10 and then nan_to_num, for the same reason: a not-quite-PSD matrix produces slightly negative eigenvalues.
Neither guard is defensive padding. Both exist because of this one line.

rbf_kernel — the one that does the work

k(x, z) = exp( −γ ‖x − z‖2 ),   γ = 12σ2 feature map: infinite-dimensional. Value is always in (0, 1]. Equals 1 only when x = z.
def rbf_kernel(X, Y=None, gamma=None, sigma=None):
    if Y is None:
        Y = X

    if gamma is not None:
        pass
    elif sigma is not None:
        gamma = 1.0 / (2.0 * sigma ** 2)
    else:
        gamma = 1.0 / (2.0 * X.shape[1])

    X_sq = np.sum(X ** 2, axis=1).reshape(-1, 1)
    Y_sq = np.sum(Y ** 2, axis=1).reshape(1, -1)
    dist_sq = np.maximum(X_sq + Y_sq - 2.0 * X @ Y.T, 0.0)
    return np.exp(-gamma * dist_sq)

Read γ as an inverse radius of influence. Small γ → a point's influence reaches far → K is warm everywhere → the model is nearly linear and underfits. Large γ → influence collapses to almost nothing → K approaches the identity matrix → every point is its own island and the model memorises the training set. The heatmap at the top of this page is that sentence, animated.

Line by line — including the three lines that look weirdthe important one
LineWhat it does, and why

Written as pass rather than restructured so the three-way priority reads top to bottom: gamma wins → else derive from sigma → else fall back to a default. Slightly unusual style, completely defensible.
gamma = 1.0 / (2.0 * sigma ** 2)The textbook conversion between the two parameterisations of the same kernel. σ is a width (a distance); γ is its inverse-square. Same kernel, two dialects — the code accepts both.
gamma = 1.0 / (2.0 * X.shape[1])The default when the caller gives neither. X.shape[1] is d, the number of features, so this is γ = 1/(2d), i.e. σ2 = d. The reasoning: squared distances tend to grow with dimension, so the width should grow with dimension too, otherwise every kernel value would underflow to zero on high-dimensional data. Say in your report that this is a heuristic default, not a tuned value. It also differs from scikit-learn's default, which additionally divides by the variance of X — so don't claim the two libraries agree here.
X_sq = np.sum(X**2, axis=1).reshape(-1, 1)The squared norm ‖xi‖² of each row, reshaped to a column (n×1).
Y_sq = np.sum(Y**2, axis=1).reshape(1, -1)Same for Y, reshaped to a row (1×m). The two different reshapes are the entire trick of the next line.
X_sq + Y_sq - 2.0 * X @ Y.TThis is ‖x − z‖2 = ‖x‖2 + ‖z‖2 − 2x·z from Idea 1 — applied to all pairs at once. Adding an (n×1) column to a (1×m) row broadcasts into an (n×m) grid where entry (i,j) already contains ‖xi‖²+‖yj‖². Subtract the (n×m) matrix of dot products and every cell is a squared distance. No loop, one matmul.
np.maximum(..., 0.0)A squared distance cannot be negative — but in floating point it can be, by about −1e−16, when two rows are identical or nearly so. Feed that to exp(-gamma * dist_sq) and you get a kernel value slightly above 1, which quietly breaks the PSD property that the solvers downstream depend on. This clamp is a one-word fix for a real bug.
np.exp(-gamma * dist_sq)The formula, applied elementwise. Distance 0 → exp(0) = 1 (the diagonal). Large distance → exp(−big) → 0.
Exam-ready

"Why not np.linalg.norm in a double loop?" Because that's O(n2) Python-level iterations. The expansion turns the whole thing into one call to X @ Y.T, which is BLAS, which is compiled and multithreaded. Same numbers, different order of magnitude in runtime. The identity from Idea 1 is doing work here that is purely about speed.

compute_kernel_matrix — the dispatcher

def compute_kernel_matrix(X, Y=None, kernel_type='rbf', **kwargs):
    if kernel_type == 'linear':
        return linear_kernel(X, Y, c=kwargs.get('c', 0.0))
    elif kernel_type == 'poly':
        return polynomial_kernel(X, Y, degree=kwargs.get('degree', 3), ...)
    elif kernel_type == 'rbf':
        return rbf_kernel(X, Y, gamma=kwargs.get('gamma', None), ...)
    else:
        raise ValueError(f"Unknown kernel type: {kernel_type}")

A string selects a function. That's it — but it's the reason every model class can carry kernel_type='rbf', **kernel_params in its constructor and never contain a single line of kernel maths. Swapping kernels across an entire experiment is one string.

Note kwargs.get('c', 0.0) against kwargs.get('c', 1.0) — the same parameter name has different defaults per kernel. Linear defaults to c=0 (a pure dot product); poly defaults to c=1 (which is what lets lower-degree terms into the feature map). Reading c as "one parameter" would be a mistake.

The else: raise ValueError matters more than it looks. Without it a typo like kernel_type='RBF' would fall through and return None, and you'd be debugging a crash three files away. Failing at the point of the mistake is a design decision.

kernel_diagonal — the memory optimisation you should brag about

Sometimes you only need k(xi, xi) — the diagonal. The naive route builds all n2 entries and reads n of them, throwing away 99.99% of the work.

def kernel_diagonal(X, kernel_type='rbf', **kwargs):
    """diag(K(X, X)) in closed form: O(n*d) time, O(n) memory."""
    sq = np.sum(X ** 2, axis=1)

    if kernel_type == 'linear':
        return sq + kwargs.get('c', 0.0)
    elif kernel_type == 'poly':
        return (kwargs.get('alpha', 1.0) * sq + kwargs.get('c', 1.0)) ** kwargs.get('degree', 3)
    elif kernel_type == 'rbf':
        return np.ones(X.shape[0], dtype=np.float64)

Each branch is the kernel formula with z set to x, simplified on paper first:

Kernelk(x, x) worked outCode
linearx·x + c = ‖x‖2 + csq + c
poly(α‖x‖2 + c)d(alpha*sq + c) ** degree
rbfexp(−γ·0) = 1, alwaysnp.ones(n)

The RBF branch is the one to point at. The distance from a point to itself is zero, exp(0)=1, so the answer is a vector of ones — no arithmetic performed, no data read. It is worth saying plainly that sq is computed at the top and then unused by that branch; that's a negligible O(nd) cost paid for keeping the function readable.

Where this pays off

kernel_knn.py calls this instead of compute_kernel_matrix in fit, and its comment says why: "avoids an n x n matrix built just to read it." That is why KernelKNNClassifier.kernel_matrix_bytes_ reports O(n) bytes while every other model reports O(n2). When you present the memory comparison table, KNN's number will look anomalous and you will be asked about it. This function is the answer.

center_kernel_matrix — subtracting a mean you cannot compute

PCA requires mean-centred data. KPCA needs the data centred in feature space — but you can't compute φ̄ = 1n Σ φ(xi), because you can't compute φ. Idea 2 again.

The fix: work out algebraically what centring would do to the dot products, and apply that to K directly.

Kc = K − 1nK − K1n + 1nK1n 1n is the n×n matrix filled entirely with 1/n
def center_kernel_matrix(K, K_train=None):
    n = K.shape[0]
    if K_train is None:
        one_n = np.ones((n, n)) / n
        return K - one_n @ K - K @ one_n + one_n @ K @ one_n
    else:
        n_train = K_train.shape[0]
        one_n_test = np.ones((K.shape[0], n_train)) / n_train
        one_n_train = np.ones((n_train, n_train)) / n_train
        return (K - one_n_test @ K_train
                - K @ one_n_train
                + one_n_test @ K_train @ one_n_train)
Where those four terms come from — the derivation in four linesworth 10 minutes

Centred feature vector: φ̃(xi) = φ(xi) − φ̄. The centred kernel is its dot product with another one:

K̃ij = (φi − φ̄)·(φj − φ̄)
    = φi·φj − φi·φ̄ − φ̄·φj + φ̄·φ̄

Now translate each of the four terms back into things you can actually compute:

TermBecomesMeaning in plain wordsCode
φi·φjKijthe raw entryK
φ̄·φj1nΣa Kajmean of column jone_n @ K
φi·φ̄1nΣb Kibmean of row iK @ one_n
φ̄·φ̄1n2Σab Kabgrand mean of the whole tableone_n @ K @ one_n

So the intimidating formula is just: subtract the row mean, subtract the column mean, add back the grand mean (added back once because subtracting both means removed it twice). It is exactly the double-centring you'd do to a two-way table in statistics.

Now the else branch. A test point must be centred using the training mean, never its own — otherwise the transform depends on which test points happen to arrive together, and your test set has leaked into itself. That is why every mean in the second branch is divided by n_train and computed from K_train, not from K. Same formula, all statistics sourced from training. This is the kernel version of "fit the scaler on train, apply it to test."

Consequence you can predict

After centring, the columns of Kc sum to zero, which forces at least one eigenvalue to be exactly zero. So KPCA can never extract more than n−1 components — and sure enough, kpca.py line n_comp = min(self.n_components, n - 1). That -1 is not arbitrary; it is this fact.

04 — kernel_ridge.py

The whole algorithm is one line.

No iteration, no convergence, no random seed. Solve one linear system and you're done. Start here — it's the cleanest illustration of the representer form.

R models/kernel_ridge.py
What it does to K: inverts it (after adding λ to the diagonal).
α = (K + λI)−1 y    →    g(x) = Σi αi k(xi, x) the file's own docstring, verbatim — the code is a transcription of it
def fit(self, X, y):
    self.X_train = X.copy()
    n = X.shape[0]

    K = compute_kernel_matrix(X, kernel_type=self.kernel_type, **self.kernel_params)
    self.kernel_matrix_bytes_ = int(K.nbytes)  # O(n^2) footprint
    A = K + self.reg_lambda * np.eye(n)
    try:
        self.alpha = solve(A, y, assume_a='pos')
    except Exception:
        # Poly kernels can lose positive-definiteness to rounding.
        self.alpha = np.linalg.lstsq(A, y, rcond=None)[0]

    return self

Statistical: it's the ridge penalty λ‖w‖², which shrinks the fit and stops it chasing noise. Numerical: K is often singular or nearly so; adding λ to every diagonal entry lifts every eigenvalue by λ, which guarantees the system is invertible. Set λ = 0 and this line — and the solver — falls over on most real data. It is doing two jobs at once.
solve(A, y, assume_a='pos')assume_a='pos' promises SciPy that A is symmetric positive-definite, so it uses Cholesky instead of general LU. Roughly half the operations, and better numerically. The promise is justified: a valid kernel gives a PSD K, and +λI pushes it to strictly positive-definite. Note also that this solves the system — it never forms (K+λI)−1. Explicitly inverting a matrix to then multiply by a vector is slower and less accurate; the formula says "inverse", the code says "solve", and the code is right.
except Exception:Reachable in practice, and the comment names the trigger: poly kernels. From the kernels.py section — degree-3 entries can reach thousands, the dynamic range wrecks the rounding, Cholesky hits a non-positive pivot and raises. Catching bare Exception is broad, but here it's a considered trade: this runs inside a sweep over many kernels and λ values, and losing an entire experiment to one bad configuration is worse than falling back.
np.linalg.lstsq(A, y, rcond=None)[0]The safety net: least squares via SVD. Slower, but it returns a sensible answer even for a singular or ill-conditioned A. [0] because lstsq returns a 4-tuple (solution, residuals, rank, singular values) and only the first is wanted.
The cost, in one sentence

Building K is O(n2d) time and O(n2) memory; the Cholesky solve is O(n3) time. That cubic term is why kernel ridge is exact and elegant and completely unusable past a few tens of thousands of points.

predict — the representer form, undisguised

def predict(self, X):
    K_test = compute_kernel_matrix(X, self.X_train, kernel_type=self.kernel_type, **self.kernel_params)
    return K_test @ self.alpha

Two arguments → K_test is m×n: row i holds the similarity of test point i to every training point. Dot that row with α and you get Σi αi k(xi, x) — the formula, exactly, with no bias term and no rearranging. If someone asks you to show them the representer theorem in code, show them this line.

KernelRidgeClassifier — regression wearing a hat

Ridge regression predicts real numbers. To make it classify, this wrapper regresses onto 0/1 targets and thresholds the output. It's a blunt instrument and it works.

CaseTargetsDecisionCode
2 classes(y == classes_[1]).astype(float) → 0 or 1score ≥ 0.5classes_[(scores >= 0.5).astype(int)]
>2 classesone 0/1 vector per classwhichever class scores highestclasses_[np.argmax(all_scores, axis=1)]

One-vs-rest (OVR): for C classes, train C separate regressors, each answering "is this class c, yes or no?", then let the most confident one win. Note the cost: C models means C kernel matrices, which is exactly what kernel_matrix_bytes_ sums up over ovr_models_.

The honest caveat, and you should volunteer it

These scores are not probabilities. Nothing constrains predict's output to [0,1] — a test point far from everything can score 1.3 or −0.4. So decision_scores returning [1.0 - s, s] gives you two columns that are usable for ROC-AUC — which only needs a ranking, not calibration — but calling them class probabilities would be wrong. The docstring is careful about this: it says "Raw regression scores per class, for ROC-AUC." Match that wording in your report.

Two small asymmetries in this file worth noticingdetail
  • KernelRidgeRegression.__init__ sets self.kernel_matrix_bytes_ = 0 as a plain attribute, then overwrites it in fit. KernelRidgeClassifier instead exposes it as a @property that sums over its sub-models. Same attribute name, two different mechanisms — the wrapper has no K of its own, so it aggregates its children's. Calling it before fit raises, because ovr_models_ is still None.
  • The binary branch trains one model, not two. Training "class A vs rest" and "class B vs rest" separately would be redundant — one score already ranks both. This is why decision_scores needs its special case: it must fabricate the second column as 1.0 - s so the output has one column per class and lines up with classes_.
05 — kernel_svm.py

The long one. But only three lines actually optimise.

You're solving for one number per training point. Most of them end up zero. The ones that don't are the support vectors.

S models/kernel_svm.py
What it does to K: indexes into it, one row at a time, thousands of times.

Why the dual, and why two at a time

An ordinary SVM asks "what weight vector w gives the widest margin?" The dual asks the equivalent question: "how hard does each training point push on the boundary?" That push is αi. And the payoff is that the data now only appears inside k(xi, xj) — never alone. Idea 2 applies, so the kernel goes in.

f(x) = Σi αi yi k(xi, x) + b,    subject to   0 ≤ αi ≤ C   and   Σi αi yi = 0 the top line is decision_function(); the two constraints are why SMO exists

Look at that equality constraint: Σ αi yi = 0. It means you cannot change one α by itself — you'd break it instantly. The smallest legal move is two at a time: nudge αi up and αj down by a compensating amount. That's SMO in one sentence: pick two, optimise them exactly (a 1-D problem with a closed-form answer), repeat.

_run_smo, in order

1. The error

E_i = float(np.sum(alpha * y * K[i, :])) + b - y[i]

How wrong the current model is about point i: Ei = f(xi) − yi. Note that np.sum(alpha * y * K[i, :]) is Σj αj yj k(xj, xi) — the same representer sum as everywhere else, just against a stored row of K instead of a freshly computed one. Because α is mostly zeros, most terms contribute nothing; the code sums them anyway, which is O(n) per point and O(n2) per epoch. A production SMO caches these errors. This one doesn't, and that's a legitimate thing to name as a limitation.

2. The KKT check — "is this point misfiled?"

if ((y[i] * E_i < -self.tol and alpha[i] < self.C) or
        (y[i] * E_i > self.tol and alpha[i] > 0)):

This looks arbitrary until you expand it. Since yi = ±1, we have yi2 = 1, so:

yiEi = yi(f(xi) − yi) = yif(xi) − 1 so y·E measures the signed margin, offset by 1

Which turns the condition into plain English:

SituationMeaningα should beViolation if
yiEi < 0margin < 1 — point is inside the margin or misclassifiedmaxed out at Calpha[i] < C
yiEi > 0margin > 1 — point is safely outsidezero — it shouldn't push at allalpha[i] > 0

If neither is true, the point is already correctly filed; skip it. tol is the tolerance band that stops the loop chasing floating-point dust forever.

3. Pick a partner — the "simplified" bit

j = i
while j == i:
    j = rng.randint(0, n)

Real SMO (Platt 1998) uses a heuristic to choose the j that makes the most progress. This picks at random. It converges more slowly and it fits in three lines — that trade is the entire meaning of the word "simplified" in the class docstring.

The reproducibility point the docstring makes for you

The class docstring calls out that j comes from a per-model RandomState, "not the unseeded global np.random, so fits are reproducible." That's a real distinction: np.random.randint would draw from a global stream that any other library could advance, making your results unrepeatable and your ablation study meaningless. And KernelSVMClassifier._make(seed_offset) passes random_state + ci, so each one-vs-rest sub-problem gets its own seed — reproducible, but not accidentally identical across classes.

4. L and H — the scary-looking part that isn't

if y[i] != y[j]:
    L = max(0, alpha[j] - alpha[i]);  H = min(self.C, self.C + alpha[j] - alpha[i])
else:
    L = max(0, alpha[i] + alpha[j] - self.C);  H = min(self.C, alpha[i] + alpha[j])

if L >= H:
    continue

Both alphas must stay inside [0, C] — that's a square box. The equality constraint forces the pair to stay on a diagonal line. Line ∩ box = a segment, and L and H are its two endpoints. Two cases because the line's slope flips sign depending on whether the labels agree. If L >= H the segment is a single point — no room to move — so skip. There's a live diagram of this in section 09; drag the sliders and the formulas stop being formulas.

5. eta — the curvature

eta = 2.0 * K[i, j] - K[i, i] - K[j, j]
if eta >= 0:
    continue

Compare with Idea 1 and this is instantly recognisable:

eta = 2k(xi,xj) − k(xi,xi) − k(xj,xj) = −‖φ(xi) − φ(xj)‖2 the negative squared distance between the two points, in feature space

So eta is normally strictly negative — the objective along the segment is a downward parabola with a clean peak, and step 6 can jump straight to it. If eta >= 0 (identical points, or a kernel that isn't quite PSD) there's no interior peak to jump to, so bail out rather than divide by zero. Note that this is the same identity as the RBF distance line and the KNN distance line. One piece of algebra, three appearances.

6. The actual optimisation — three lines

alpha[j] -= y[j] * (E_i - E_j) / eta          # jump to the peak of the parabola
alpha[j] = np.clip(alpha[j], L, H)            # drag it back into the legal segment
# ... small-step check ...
alpha[i] += y[i] * y[j] * (alpha_j_old - alpha[j])  # move i to keep Σ α y = 0

Unconstrained optimum → clip into [L, H] → move αi by exactly the amount that repairs the equality constraint. That third line is not a heuristic: it is the unique correction that keeps Σ α y unchanged. These three lines are the algorithm. Everything above them is deciding which pair to apply them to.

if abs(alpha[j] - alpha_j_old) < 1e-5:
    continue

If the step was microscopic, don't count it as progress. Without this, rounding-level wiggles would keep resetting passes to zero and the loop would never converge. It's the difference between "changed" and "meaningfully changed."

7. Repairing b

b1 = b - E_i - y[i]*(alpha[i]-alpha_i_old)*K[i,i] - y[j]*(alpha[j]-alpha_j_old)*K[i,j]
b2 = b - E_j - y[i]*(alpha[i]-alpha_i_old)*K[i,j] - y[j]*(alpha[j]-alpha_j_old)*K[j,j]

if 0 < alpha[i] < self.C:   b = b1
elif 0 < alpha[j] < self.C: b = b2
else:                        b = (b1 + b2) / 2.0

The alphas moved, so b is now stale. b1 is the value that would put point i exactly on the margin; b2 does the same for j. The choice is principled: an α strictly between 0 and C means that point is exactly on the margin (it's an unbounded support vector), so its b is the trustworthy one. If both are at a bound, neither is pinned to the margin — so average them and move on. Read the three-way branch as "prefer a witness that's actually standing on the boundary."

8. Convergence

if num_changed == 0:
    passes += 1
else:
    passes = 0

Sweep all n points. If a full sweep changed nothing, everything satisfies KKT within tol. Count max_passes consecutive clean sweeps and stop. Any change anywhere resets the counter to zero — the bar is "clean sweeps in a row", not "clean sweeps in total."

AttributeWhy it's in the class
max_passesHow many clean sweeps count as done. The convergence criterion.
max_epochsEmergency brake. The docstring: "hard ceiling on outer loops, so the fit always terminates." Without it a hard configuration could spin forever inside a grid search.
converged_passes >= self.max_passes. Records which exit you took — a real convergence, or a timeout. This is the difference between reporting a number and reporting a number you can defend.

Prediction, support vectors, and one quirkthe rest of the file 
def decision_function(self, X):
    K_test = compute_kernel_matrix(X, self.X_train, ...)
    return K_test @ (self.alpha * self.y_train) + self.b

Identical in shape to kernel ridge, with two differences: the coefficients are alpha * y_train rather than alpha (the SVM dual carries the label inside the sum), and there's a bias b. That's the whole difference between the two prediction rules.

n_support_ counts alpha > 1e-8. Not > 0, because floating point leaves dust like 1e-17 behind — those aren't support vectors, they're rounding. The points that survive are the only ones in the sum: delete every training point with α = 0 and the model is bit-for-bit identical. That's the sparsity property, and it's the one thing the SVM has that kernel ridge doesn't (ridge's α is dense — every training point contributes forever).

A quirk worth knowing before someone finds it. predict returns np.sign(...), which maps an exact zero to 0, not ±1. Then the classifier does np.where(preds >= 0, classes_[1], classes_[0]) — so a point landing exactly on the boundary is assigned classes_[1]. Probability zero on real data, but it's the kind of thing that gets asked, and "ties break toward the positive class" is a better answer than a blank look.

decision_scores returns [-s, s]** for the binary case, mirroring ridge's [1.0 - s, s]. Different because ridge regresses onto {0,1} while the SVM uses {−1,+1} targets — so ridge's "not-class" score is 1-s and the SVM's is -s. Both give a valid ranking for ROC-AUC; neither gives probabilities.

06 — kpca.py

PCA, but the covariance matrix is never built.

Ordinary PCA eigendecomposes a d×d covariance matrix. KPCA eigendecomposes the n×n kernel matrix instead — and gets nonlinear components for it.

P models/kpca.py
What it does to K: centres it, then takes its eigenvectors.

The swap that makes it work

Ordinary PCAKernel PCA
Decomposescovariance, d×dkernel matrix, n×n
Eigenvector lengthd — a direction in input spacen — one weight per training point

Read the second row twice, because it's where people get lost. In KPCA an eigenvector is not a direction you can plot. It's a length-n vector of coefficients a, and the actual principal component lives in feature space as v = Σi ai φ(xi) — unbuildable, again. The representer theorem, again. Everything in this codebase is one weight per training point.

fit — five moves

def fit(self, X):
    self.X_train = X.copy()
    n = X.shape[0]

    K = compute_kernel_matrix(X, kernel_type=self.kernel_type, **self.kernel_params)
    self.K_train = K
    self.kernel_matrix_bytes_ = int(K.nbytes)

    K_centered = center_kernel_matrix(K)

    n_comp = min(self.n_components, n - 1)
    eigenvalues, eigenvectors = eigh(K_centered, subset_by_index=[n - n_comp, n - 1])

    idx = np.argsort(eigenvalues)[::-1]
    self.eigenvalues = eigenvalues[idx]
    self.eigenvectors = eigenvectors[:, idx]

    for i in range(len(self.eigenvalues)):
        if self.eigenvalues[i] > 1e-10:
            self.eigenvectors[:, i] /= np.sqrt(self.eigenvalues[i])

    return self
Line by line — the four lines that need explainingdo not skip
LineWhat it does, and why
self.K_train = KStored, not discarded — unlike in ridge. transform() needs it later to centre test points against the training mean. This is the price of doing centring correctly, and it means a fitted KPCA holds an n×n matrix in memory for its whole life.
K_centered = center_kernel_matrix(K)One argument → the training branch of that function → the double-centring from the kernels.py section. PCA on uncentred data measures the wrong thing: the first component would just point at the mean instead of at the direction of maximum variance. Not optional.
n_comp = min(self.n_components, n - 1)Two caps in one line. You can't have more components than points; and centring itself destroys one degree of freedom (the columns of Kc now sum to zero, forcing an eigenvalue to be exactly 0). Hence n - 1, not n. Ask for 50 components from 30 points and you silently get 29 — worth knowing when your output array is narrower than you expected.
eigh(K_centered, subset_by_index=[n - n_comp, n - 1])eigh is the symmetric/Hermitian solver — valid because K is symmetric, and roughly twice as fast as the general eig while guaranteeing real eigenvalues. subset_by_index asks for only the eigenvectors you'll keep, instead of computing all n and throwing most away. The indices [n-n_comp, n-1] mean "the top n_comp" because eigh returns results in ascending order — the largest live at the end.
idx = np.argsort(eigenvalues)[::-1]Reverse to descending, so component 0 is the one that explains the most variance. The [:, idx] reorders columns, because eigh returns eigenvectors as columns. Getting this wrong (reordering rows) is a classic silent bug — the shapes still work and the output is garbage.
if eigenvalues[i] > 1e-10:The guard. A near-zero eigenvalue would make sqrt tiny and the division explode; a negative one — which a poly kernel that has rounded its way out of PSD will hand you — would make np.sqrt return nan. Rather than crash, skip the normalisation for that component. This is the same root cause as ridge's try/except, showing up in a different file.
eigenvectors[:, i] /= np.sqrt(eigenvalues[i])The line everyone asks about. See below.

Why divide by √λ

We want the principal component in feature space, v = Σi aiφ(xi), to be a unit vector — that's what makes a projection onto it a genuine coordinate. Work out its length using only kernels:

‖v‖2 = Σi,j aiaj φ(xi)·φ(xj) = a⊤Kca = a⊤(λa) = λ‖a‖2 using Kca = λa, the definition of an eigenvector

eigh hands back a with ‖a‖ = 1, so ‖v‖2 = λ — too long by a factor of √λ. Divide a by √λ and ‖v‖ = 1. So the division normalises a vector you never built, by adjusting the coefficients of a vector you did. That sentence is the whole of KPCA in miniature, and it's a good thing to have memorised.

transform vs fit_transform — and why they aren't the same code

def transform(self, X):
    K_test = compute_kernel_matrix(X, self.X_train, ...)      # m×n
    K_test_centered = center_kernel_matrix(K_test, self.K_train)  # TWO args
    return K_test_centered @ self.eigenvectors

def fit_transform(self, X):
    self.fit(X)
    K_centered = center_kernel_matrix(self.K_train)                # ONE arg
    return K_centered @ self.eigenvectors

Same last line, different centring. fit_transform centres the training kernel against itself; transform centres the test kernel against the training statistics. Passing one argument where you meant two is a data leak that will inflate your test scores and look like a good result. The two-argument call is the correct one for anything that isn't the training set.

And the projection line is, once more, the representer form: a row of (centred) kernel values against the training set, dotted with learned per-point coefficients.

A neat identity: what fit_transform actually returnsoptional but impressive

Take the normalised eigenvector ã = a/√λ and push the training data through:

Kc ã = Kc a / √λ = λa / √λ = √λ · a

So the training projections are just the original eigenvector scaled by √λ. Two things follow, both useful in a report:

  • The spread of each output column is set by √λ. Column 0 has the widest spread because it has the largest eigenvalue. That's "explains the most variance," made concrete.
  • You could compute the training projections without the matmul at all. The code does the matmul anyway — because it makes fit_transform and transform visibly the same operation, and clarity beats saving one O(n2) multiply that you already paid for many times over.

KPCAClassifier — two stages bolted together

def fit(self, X, y):

    self.kpca = KernelPCA(n_components=..., kernel_type=..., **self.kernel_params)

KPCA doesn't classify — it's unsupervised, and its fit takes no y. So this wrapper does reduce, then classify: project into n_components dimensions, hand the result to a plain logistic regression. The comparison it enables is the interesting one: can a linear classifier on nonlinear features match a nonlinear classifier on raw features? That's KPCA+logreg versus kernel SVM, and it's the experiment worth reporting.

07 — kernel_knn.py

The file that is honest about being pointless.

Read its docstring first. The author tells you, in advance, that two of the three kernels change nothing here. That candour is the most valuable thing in the file.

N models/kernel_knn.py
What it does to K: turns it into distances — and never builds the training half of it at all.

Distance from similarity

KNN needs distances. A kernel gives similarities. Idea 1 converts between them for free:

d2(x, z) = ‖φ(x) − φ(z)‖2 = k(x,x) + k(z,z) − 2k(x,z) the distance in feature space, computed entirely from kernel values
dists = np.maximum(
    K_diag_test.reshape(-1, 1) + self.K_diag_train.reshape(1, -1) - 2.0 * K_cross,
    0.0
)

Compare that against the middle of rbf_kernel and against eta in the SVM. Same identity, third appearance. Column + row broadcasts to a grid; np.maximum(..., 0.0) clamps the floating-point negatives; the result is an m×n table of squared distances. Note it never takes a square root — argpartition only needs a ranking, and √ is monotone, so the root would cost time and change nothing.

The docstring's admission — and why it's the best paragraph in the codebase

Substitute each kernel into the distance formula and watch what happens:

Kerneld² becomesEffect on the neighbour list
linear (c=0)‖x‖2 + ‖z‖2 − 2x·z = plain Euclidean²None. It is ordinary KNN.
rbf1 + 1 − 2k = 2 − 2k(x,z)None. k decreases monotonically with Euclidean distance, so the ordering is identical. Same neighbours, always — for every γ.
poly(α‖x‖2+c)d + (α‖z‖2+c)d − 2(αx·z+c)dGenuinely different. Not monotone in Euclidean distance — the norm terms enter at degree d and can dominate.

So when your results table shows linear-KNN and RBF-KNN with identical accuracy to the last decimal, that is not a bug — it is the mathematics, predicted in advance by the person who wrote the file. Reporting it as a finding, with this derivation, is worth more than any accuracy number in the table. Note the γ-independence too: it's the sharpest possible demonstration that a kernel only helps when the algorithm uses the geometry it induces, not just the ordering.

fit — the file's best decision

def fit(self, X, y):
    self.X_train = X.copy()
    self.y_train = y.copy()
    self.classes_ = np.unique(y)
    # Closed-form diagonal: avoids an n x n matrix built just to read it.
    self.K_diag_train = kernel_diagonal(X, kernel_type=self.kernel_type, **self.kernel_params)
    self.kernel_matrix_bytes_ = int(self.K_diag_train.nbytes)
    return self

There is no training here — no α, no solve, no iteration. KNN is a lazy learner: it memorises and defers. The only computation is the diagonal, and it uses kernel_diagonal rather than compute_kernel_matrix, so this class stores O(n) bytes where every other model stores O(n2). On 10,000 points that's 80 KB against 800 MB — four orders of magnitude, from choosing the right function. Expect to be asked about the anomalous row in your memory table; this line is the answer.

Two real snags in this file

1. predict_proba is stateful. It calls self.predict(X) purely for the side effect of filling self._last_proba, then returns that attribute. So calling predict_proba silently doubles the work if you already called predict, and the attribute always reflects the most recent call — read it after predicting on a different X and you get the wrong array with no warning. It works as written; it's fragile as a pattern.

2. A latent edge case in the regressor. KernelKNNRegressor uses k_actual = min(self.k, len(self.X_train)) — no -1, unlike the classifier. But np.argpartition(arr, kth) requires kth to be a valid index, i.e. strictly less than the array length. So if you ever set k equal to the number of training points, the classifier survives and the regressor raises. Never triggered at sensible k values, and I'd flag it in a code review rather than in a results section — but it's exactly the kind of asymmetry a marker enjoys finding, so notice it before they do.

The regressor is otherwise the classifier with the vote swapped for an average: predictions.append(np.mean(nn_values)). Same distances, same argpartition, different final line. And y.astype(np.float64) rather than .copy() — because averaging integer labels would truncate.

10 — Defend it

The questions you'll actually get.

Answer out loud before revealing. If you can't, the section link next to the answer is where to go back to.

1. What is the kernel trick, in two sentences, without saying "higher dimensional space" and stopping there?

These algorithms only ever touch the data through dot products between pairs of points. So you can replace that dot product with any function that returns what a dot product in some richer space would have returned — getting the nonlinear model without ever computing the coordinates in that space. Evidence: φ appears nowhere in these five files.

2. Why is the SMO working set two alphas and not one?

The dual has the equality constraint Σ αiyi = 0. Moving one α alone breaks it. Two is the smallest set that can move while keeping the sum fixed — that's why alpha[i] += y[i]*y[j]*(alpha_j_old - alpha[j]) exists.

3. A = K + self.reg_lambda * np.eye(n) — give both reasons.

Statistical: it's the ridge penalty, shrinking the fit away from noise. Numerical: it lifts every eigenvalue by λ, making a possibly-singular K strictly positive-definite so Cholesky (assume_a='pos') is valid. One line, two jobs.

4. Why does kernel_knn report O(n) memory when everything else reports O(n²)?

Its fit calls kernel_diagonal, not compute_kernel_matrix. It only ever needs k(x,x), and each kernel's diagonal has a closed form — for RBF it's a vector of ones with no arithmetic at all. Building n² entries to read n of them would be the naive route. (§03, §07)

5. Your table shows linear-KNN and RBF-KNN with identical accuracy. Bug?

No — and the docstring predicts it. Linear gives exactly Euclidean distance. RBF gives d2 = 2 − 2k, which is monotone in Euclidean distance, so the ranking of neighbours is unchanged for any γ. Only poly reorders anything. It's a demonstration that a kernel only helps when the algorithm uses the induced geometry, not just the ordering. (§07)

6. Why divide the KPCA eigenvectors by √λ?

The component in feature space is v = Σ aiφ(xi), and ‖v‖2 = a⊤Kca = λ‖a‖2. eigh returns ‖a‖ = 1, so v is too long by √λ. Dividing a by √λ normalises a vector you never constructed. (§06)

7. Why does center_kernel_matrix take a second argument?

Test points must be centred using the training mean, not their own — otherwise the transform depends on which test points arrive together and the test set leaks into itself. The else branch sources every mean from K_train and divides by n_train. It's the kernel version of fitting a scaler on train only. (§03, §06)

8. What's np.maximum(..., 0.0) guarding against, and where does it appear?

Floating-point error can make a computed squared distance come out at about −1e−16 for identical or near-identical points. In rbf_kernel that would give a kernel value above 1 and break PSD; in kernel_knn it would corrupt the distance table. It appears in rbf_kernel and twice in kernel_knn. (§03, §07)

9. What does converged_ buy you that accuracy doesn't?

It says whether the fit finished or ran out of max_epochs. A truncated fit's accuracy is not a property of the method — it's a property of your budget. Reporting the two separately is the difference between a result and a claim. (§05)

10. Point at the representer theorem in three different files.

K_test @ self.alpha (ridge), K_test @ (self.alpha * self.y_train) + self.b (SVM), K_test_centered @ self.eigenvectors (KPCA). All the same shape: kernel values against the training set, dotted with one learned coefficient per training point. And np.sum(alpha * y * K[i, :]) inside SMO is the same sum against a cached row. (§01, §08)

11. What makes this SMO "simplified", and what does it cost?

The second index j is drawn at random rather than by Platt's heuristic, and the errors Ei are recomputed from scratch each time instead of cached. Both are correct; both are slower to converge. It costs epochs, not correctness. (§05)

12. Which of these methods gives you a sparse model, and why does that matter?

Only the SVM. Its α is mostly zero — n_support_ counts what survives. Delete every training point with α = 0 and the model is bit-for-bit identical, so prediction cost scales with the number of support vectors rather than with n. Kernel ridge's α is dense: every training point contributes to every prediction, forever. (§05, §08)
